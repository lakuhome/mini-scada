# mini-scada

Легковесная веб-ориентированная система сбора данных и диспетчерского управления (SCADA) на чистом асинхронном Python (`asyncio`).

Проект соединяет промышленный контроллер (ПЛК с датчиками) и веб-интерфейс оператора: опрашивает контроллер по протоколу Modbus TCP, обрабатывает измерения в оперативной памяти, отсекает шум, сохраняет историю в SQLite и транслирует данные клиентам в реальном времени.

> **Статус проекта:** Подготовка к Контрольной точке 1 (КТ-1, редакция КТП 12.2).  
> **Фиксированный тег репозитория:** `kt01-v1`

## 1. Устав проекта (Карточка КТ-1)

| Пункт устава | Описание и инженерный ответ |
|---|---|
| **Команда проекта** | Студенческая команда разработчиков (роли: инженер системного сбора/Modbus, разработчик ядра и шины данных, веб-разработчик). |
| **Кто пользователь?** | Дежурный оператор-диспетчер / инженер АСУ ТП малой котельной или насосной станции. |
| **Какую задачу решает?** | Непрерывный удаленный мониторинг технологических параметров (температура, давление, статус насосов), контроль аварийных состояний оборудования и оперативное изменение уставок без нахождения в шумном цеху. |
| **Как решает сейчас?** | Физический обход щитов автоматики с журналом либо эксплуатация дорогих зарубежных SCADA (WinCC, InTouch), лицензии на которые недоступны, а запуск требует тяжелых выделенных серверов. |
| **Собственные правила и логика в коде** | 1. **Фильтрация шума (`DeadbandFilter`):** отсечение микроколебаний (`|Δ| < threshold`), предотвращающее деградацию диска.<br>2. **Валидация качества данных (`Tag.update_value` / `Tag.set_bad_quality`):** отсечение `NaN`/`None` и автоматический перевод тегов в статус `"BAD"` при таймауте сокета или потере связи.<br>3. **Валидация уставок:** проверка допустимого физического диапазона значений перед отправкой бинарной команды записи в контроллер (FC 06). |
| **Модуль для изолированного наблюдения** | **`DeadbandFilter`** (замер коэффициента сжатия данных и накладных расходов памяти/CPU при потоке 1000+ точек/сек) и **`PollingEngine`** (замер времени кругового опроса RTT и джиттера при имитации сетевых задержек). |
| **Внешние ресурсы** | **Сеть:** TCP-сокеты по протоколу Modbus TCP (порт 5020) и HTTP/WebSockets для клиентов.<br>**Файловая система / БД:** файл базы данных SQLite3 в асинхронном режиме WAL. |

## 2. Архитектура и сквозной сценарий

Вся система работает в **одном асинхронном процессе Python** (`asyncio` Event Loop):

```text
[ ПЛК / Симулятор ] 
        │
        │  Modbus TCP (порт 5020)
        ▼
[ Polling Engine ] ──────> [ InMemoryBus ]
(опрос раз в 1 сек)        (актуальные теги в RAM)
                                 │            │
             (архив в фоне)      │            │  (живой экран)
                                 ▼            ▼
                        [ DeadbandFilter ]  [ WebSockets ]
                                 │            │
                                 ▼            ▼
                         [ База SQLite ]  [ Браузер ]
```

## 3. Быстрый запуск и минимальный исполняемый компонент (КТ-1)

Минимальный компонент удовлетворяет всем требованиям пункта 6 регламента КТ-1: запускается из чистого клона, принимает параметры конфигурации, сообщает версию/сборку, выдает диагностическую запись и имеет проверяемый признак успешного запуска.

### 3.1. Подготовка окружения (чистый клон)
Требуется Python 3.11+.

```bash
# 1. Клонирование репозитория
git clone https://github.com/lakuhome/mini-scada.git
cd mini-scada

# 2. Создание и активация виртуального окружения
python -m venv venv

# Windows (PowerShell):
.\venv\Scripts\Activate.ps1
# Linux / macOS:
source venv/bin/activate

# 3. Установка зависимостей
pip install -r requirements.txt
```

### 3.2. Проверяемый признак успешного запуска (Self-Check / Smoke-тест)
Выполняет автоматическую диагностику шины данных, фильтра зоны нечувствительности и сериализации сетевых пакетов Modbus TCP:
```bash
python -m src.main --check
```
**Ожидаемый вывод (код возврата `0`):**
```text
[HEALTHCHECK: OK] Version: 0.1.0-kt1 | Build: 2026.09.21-kt1 | Mode: self-check | Status: ALL SYSTEMS OPERATIONAL
```

### 3.3. Сквозная демонстрация (All-in-One: Симулятор + Опрос + Шина + Фильтр)
Запуск полноценного сквозного сценария в одном терминале с настраиваемыми параметрами конфигурации:
```bash
# Запуск симулятора и опроса (порт 5020, период 1 сек, deadband 0.5):
python -m src.main --simulate --port 5020 --interval 1.0 --threshold 0.5
```

### 3.4. Раздельный запуск компонентов (в разных терминалах)
* **Терминал 1 (Виртуальный контроллер ПЛК):**
  ```bash
  python -m src.main --mode plc --port 5020
  # Либо напрямую: python -m src.simulator.virtual_plc
  ```
* **Терминал 2 (Движок опроса Polling Engine):**
  ```bash
  python -m src.main --mode poll --host 127.0.0.1 --port 5020 --interval 1.0
  # Либо напрямую: python -m src.da.polling_engine
  ```

### 3.5. Запуск автоматических тестов
```bash
pytest -v
```

## 4. Правила работы команды и Git Flow

В соответствии с регламентом КТП проект следует дисциплине инженерной разработки:
1. **Порядок внесения изменений:**
   $$\text{Задача в бэклоге} \longrightarrow \text{Тематическая ветка} \longrightarrow \text{Изменения + Тесты} \longrightarrow \text{PR} \longrightarrow \text{Review} \longrightarrow \text{Merge в main}$$
2. **Защита ветки `main`:** Прямой `git push` в ветку `main` запрещен. Все изменения попадают только через Pull Request с успешным прохождением CI.
3. **Непрерывная интеграция (CI):** При каждом Push и PR на GitHub автоматически запускается конвейер GitHub Actions (`.github/workflows/ci.yml`), выполняющий линтинг и запуск `pytest`.
4. **Фиксация контрольной точки:** Сдаваемое состояние закреплено тегом:
   ```bash
   git tag -a kt01-v1 -m "Фиксация состояния репозитория к КТ-1"
   git push origin kt01-v1
   ```
