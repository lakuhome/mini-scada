## 1. Карточка изменения

Идентификатор: CR-001.

Автор требования: [указать фактического автора].

Согласование преподавателем: [указать фактическую отметку и дату].

### Новое требование

При ошибке сохранения значения тега в SQLite система не должна считать это значение успешно архивированным. Состояние Deadband должно обновляться только после успешного сохранения либо восстанавливаться после неудачной записи.

### Причина изменения

При обновлении состояния Deadband до завершения записи SQLite ошибка сохранения могла привести к тому, что последующее поступление аналогичного значения ошибочно отфильтровывалось бы, несмотря на отсутствие записи в истории.

## 2. Анализ влияния изменения

| Свойство | До CR-001 | После CR-001 | Что необходимо обновить |
|---|---|---|---|
| Граница модуля | StorageService обращается к Database и DeadbandFilter | Внешняя граница SQLite сохраняется. Внутренний интерфейс Deadband разделён на проверку и подтверждение | Модульная карта, ADR |
| Владелец ресурса | Database владеет соединением SQLite | Владелец не изменился | Зафиксировать неизменность в таблице границ |
| Передача владения | StorageService использует Database без передачи владения соединением | Порядок заимствования не изменился | Зафиксировать неизменность |
| Требования к освобождению | Соединение закрывается при завершении приложения | Порядок закрытия сохраняется; при ошибке транзакции предусмотрена попытка rollback | Таблица системных границ |
| Частичный отказ | Состояние Deadband могло измениться до успешного сохранения | Deadband обновляется после успешного commit. При исключении подтверждение не выполняется | ADR, модульная карта, таблица границ, тесты |

## 3. Изменения реализации

### DeadbandFilter

Добавлен двухфазный интерфейс:

- would_store — проверка необходимости архивирования без изменения состояния;
- mark_stored — фиксация значения после успешного сохранения.

Метод should_store сохранён для совместимости.

### StorageService

Операция архивирования выполняется в следующем порядке:

1. Проверка значения посредством would_store.
2. Сохранение через Database.save_tag.
3. Обновление Deadband через mark_stored.

При исключении третий этап не выполняется.

### Database

При ошибке выполнения INSERT или commit предпринимается попытка отката транзакции через rollback.

## 4. Обоснование неизменности архитектуры

CR-001 не требует создания нового модуля, изменения владельца соединения SQLite или передачи владения ресурсом.

Изменение реализуется внутри существующих компонентов Database, StorageService и DeadbandFilter.

Границы PollingEngine, VirtualPLC и REST API не изменяются.

## 7. Вывод

CR-001 изменяет порядок подтверждения архивирования и поведение модуля при частичном отказе. Существующая модульная структура и владельцы системных ресурсов сохраняются.

## 8. Фактические результаты проверки

Специализированное тестирование Р5 и CR-001: 7 тестов успешно пройдены за 1,39 секунды.

Регрессионное тестирование проекта: 117 тестов успешно пройдены за 10,29 секунды.

При моделировании ошибки commit подтверждено:

- транзакция завершена откатом;
- ошибочная запись отсутствует в истории;
- состояние Deadband не изменилось;
- повторная операция сохранения выполнена успешно;
- после завершения работы соединение закрыто.
