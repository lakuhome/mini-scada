# Протокол предпроектного обследования (КТ-1)

* **Дата проведения:** 21 сентября 2026 г.
* **Участники:** Команда разработки mini-scada.
* **Респондент / Роль заказчика:** Преподаватель (в роли Главного инженера АСУ ТП / Ведущего диспетчера котельной).

---

## 1. Контекст и предметная область

Обследуется малый технологический узел: модульная газовая котельная / насосная станция водоснабжения.
В настоящее время дежурный персонал либо вынужден периодически совершать физический обход шкафов автоматики, либо на объекте эксплуатируется устаревшая, тяжеловесная SCADA-система иностранного вендора, лицензия на которую закончилась, а запуск требует отдельной дорогостоящей серверной инфраструктуры (Windows Server, MS SQL).

Цель проекта: развернуть легковесный, независимый от вендоров программный комплекс для непрерывного опроса контроллеров по Modbus TCP, отображения параметров на легковесном мнемощите в браузере и надежного архивирования аварийных трендов.

---

## 2. Ключевые вопросы и результаты интервью

### Как выглядит основной сценарий работы?
1. Оператор открывает веб-страницу диспетчерского пульта на любом рабочем месте в локальной сети предприятия.
2. Система непрерывно с частотой 1 раз в секунду опрашивает контроллер узла (ПЛК).
3. На экране отображаются текущие физические параметры: температура прямой и обратной воды, давление в контуре, состояние насосов (вкл/выкл) и уставки.
4. При возникновении нештатной ситуации (разрыв кабеля связи, зависание контроллера, выход давления за аварийный предел) оператор немедленно видит изменение индикатора качества на «НЕДОСТОВЕРНО (BAD)» и тревожный статус.
5. При необходимости оператор отправляет команду изменения уставки (например, целевой температуры теплоносителя).

### Какие данные поступают и какой результат нужен?
* **Входные данные:** Поток 16-битных регистров по протоколу Modbus TCP (Holdings Registers 0–4):
  * Регистр 0: Температура котла (масштабированное целое, например 755 = 75.5 °C).
  * Регистр 1: Давление теплоносителя (например, 210 = 2.10 бар).
  * Регистр 2: Состояние сетевого насоса (0 — остановлен, 1 — работает).
  * Регистр 3: Код аварии / диагностический статус ПЛК.
  * Регистр 4: Текущая уставка регулятора.
* **Выходной результат:**
  * Актуальная таблица/мнемосхема в браузере с временем задержки обновления не более 1–1.5 секунд.
  * Архивный журнал изменений параметров в базе данных (без засорения шумом датчиков).
  * Фиксация событий потери и восстановления связи.

### Какие ограничения и ошибки существенны?
1. **Обрыв связи и таймауты:** Проводная сеть в цеху подвержена помехам. Потеря одного пакета не должна ронять сервер. При устойчивом обрыве (более 2-3 сек) оператор обязан видеть статус «BAD», а не «замерзшие» последние цифры.
2. **Защита от переполнения диска:** Датчики температуры шумят в десятых долях градуса каждую секунду. Прямая поминутная запись сотен тысяч идентичных точек забьет диск за недели. Обязательна фильтрация микроколебаний (Deadband).
3. **Защита от ошибочных уставок:** Оператор не должен иметь возможности записать аварийное значение (например, температуру 500 °C при максимуме котла 110 °C).

### По каким признакам пользователь поймёт, что задача решена?
1. Сервер запускается из одной команды в чистом окружении без сторонних СУБД.
2. Симулятор генерирует изменение показаний, и они без задержек транслируются в веб-интерфейс.
3. При отключении симулятора интерфейс штатно показывает статус недостоверности (BAD) и пытается восстановить сессию.
4. При восстановлении связи опрос возобновляется автоматически.

## 3. Разграничение потребностей и гипотез

| Подтвержденные потребности заказчика | Рабочие гипотезы команды (подлежат проверке на следующих КТ) |
|---|---|
| 1. Немедленная индикация обрыва связи (статус качества BAD). | 1. Зона нечувствительности 0.5 °C достаточна для сокращения объема архива на 80–90%. |
| 2. Работа по стандартному протоколу Modbus TCP без закрытых библиотек. | 2. Производительности SQLite в режиме WAL достаточно для обслуживания 50–100 тегов в одном процессе. |
| 3. Защита от дребезга данных перед архивацией. | 3. Веб-интерфейс на чистом Vanilla JS без React/Vue будет проще в сопровождении и быстрее в развертывании. |
| 4. Запуск на локальном ПК диспетчера без тяжелых серверов. | 4. Механизм переподключения с интервалом в 3 секунды оптимален при временных сбоях в промышленных сетях. |
