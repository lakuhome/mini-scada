* **Статус:** Принято

## 1. Контекст

Мы разрабатываем `mini-scada` — учебную и прикладную систему для опроса контроллеров и показа данных в браузере.
Разработка ведется на личных компьютерах с Windows, а запуск и тестирование планируются также на виртуальных машинах с Linux.

Основные требования к стеку:
1. Простота и наглядность: чтобы любой студент мог разобраться в коде и проследить путь байтов от регистра до экрана.
2. Отсутствие тяжелых внешних сервисов (Redis, RabbitMQ, отдельные серверы баз данных), чтобы проект запускался из чистого клона за одну команду.
3. Надежная работа с сетью в реальном времени (цикл опроса 1 раз в секунду).

## 2. Выбранные технологии и почему именно они

### Python 3.11+ и библиотека `asyncio`
* **Почему:** у участников команды есть базовые знания Python. Асинхронность (`asyncio`) идеально подходит для работы с сетью: пока программа ждет ответ от контроллера по сокету или передает данные в WebSocket, процессор не простаивает и не блокируется. При этом все выполняется в одном потоке, поэтому нет сложных блокировок и конфликтов за память при работе с шиной тегов.

### Сеть и протокол: рукописный Modbus TCP поверх сокетов и модуля `struct`
* **Почему:** мы не используем тяжелые сторонние библиотеки для Modbus (вроде полного пакета pymodbus для логики сбора), потому что пишем ядро сами. Протокол Modbus TCP состоит из простого заголовка MBAP (7 байт) и данных (PDU). С помощью встроенного в Python модуля `struct` мы сами пакуем и распаковываем эти байты. Это дает полный контроль над ошибками связи и таймаутами.

### Веб-сервер: FastAPI и WebSockets
* **Почему:** FastAPI работает нативно с `asyncio` через Uvicorn, легко отдает статические файлы (HTML, JS, CSS) и поддерживает WebSockets из коробки. Для фронтенда мы используем чистый HTML/JS без React и сборщиков (Webpack/Vite), чтобы не усложнять запуск проекта.

### Хранилище: встроенная SQLite
* **Почему:** SQLite не требует установки отдельного сервера базы данных, вся база хранится в одном файле рядом с проектом. Для наших задач (сохранение отфильтрованных показаний пары датчиков) производительности SQLite более чем достаточно.

## 3. Инструменты разработки (7 позиций КТП)

В соответствии с требованиями КТ-1 выбраны инструменты по всем 7 направлениям и намечен план их использования:

| № | Направление | Выбранный инструмент | Как используется | План на семестр |
|---|---|---|---|---|
| 1 | **Окружение и сборка** | `venv` | Изоляция зависимостей Python в локальной папке проекта | На КТ-1 используется `venv`, для удобства позже подготовим Dockerfile |
| 2 | **Управление зависимостями** | `pip`, `requirements.txt` | Установка библиотек одной командой `pip install -r requirements.txt` | Фиксация точных версий библиотек |
| 3 | **Автоматические тесты** | `pytest`, `pytest-asyncio` | Проверка шины, фильтра шума, разбора пакетов Modbus и самодиагностики | Добавление тестов на разрывы соединения и запись в базу |
| 4 | **Статический анализ** | `ruff` | Быстрая проверка стиля кода и ошибок линтером | Регулярный запуск линтера перед коммитами |
| 5 | **Отладка и диагностика** | `logging`, команда `--check` | Вывод диагностических сообщений в консоль с отметками времени и уровнями (INFO, ERROR) | Добавление понятных логов сбоев сети |
| 6 | **Профилирование** | `cProfile` | Встроенный профилировщик Python для замера времени выполнения функций | Замер производительности фильтра шума под нагрузкой |
| 7 | **Автоматические проверки в CI** | GitHub Actions | Запуск тестов при каждом пуше и pull request (`.github/workflows/ci.yml`) | Контроль прохождения тестов на Ubuntu runner |
