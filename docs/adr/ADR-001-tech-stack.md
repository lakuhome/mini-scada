# ADR-001: Выбор технологического стека и инструментального контура

* **Статус:** Принято (Accepted)
* **Дата:** 21 сентября 2026 г.
* **Контекст:** Контрольная точка 1 (КТ-1), определение базового стека и маршрута инструментов.

---

## 1. Контекст и проблема

Разрабатывается легковесная SCADA-система (`mini-scada`) для автономного мониторинга промышленных объектов (котельные, насосные станции).  
Требования к продукту:
1. Возможность работы в реальном времени с циклом опроса 1 секунда и минимальной задержкой доставки до оператора (< 100 мс в памяти).
2. Независимость от закрытых проприетарных платформ и тяжелых внешних сервисов (брокеров сообщений, отдельных баз данных на начальном этапе).
3. Воспроизводимость запуска на любой машине из чистого репозитория студенческой командой.
4. Высокая тестируемость низкоуровневого сетевого взаимодействия и алгоритмов фильтрации.

---

## 2. Принятые решения и обоснование

### 2.1. Среда и модель исполнения: Python 3.11+ и чистый `asyncio`
* **Решение:** Единый асинхронный процесс (`asyncio` Event Loop) на Python 3.11+.
* **Обоснование:**
  * Операции опроса Modbus и рассылки по WebSockets являются строго I/O-bound (ожидание сетевых ответов). Асинхронный цикл переключает задачи с микросекундным оверхедом без тяжелых системных потоков ОС.
  * Исключаются гонки данных (data races) и взаимные блокировки (deadlocks) при доступе к `InMemoryBus`: состояние разделяется внутри одного потока и изменяется предсказуемо.
  * Python 3.11 содержит существенные оптимизации производительности генераторов и асинхронных тасок (+15-25% по сравнению с 3.10).

### 2.2. Протокол связи с контроллерами: Рукописный Modbus TCP поверх сокетов и `struct`
* **Решение:** Отказ от монструозных библиотек (вроде полного фреймворка `pymodbus` для базового сбора) в пользу собственной реализации сетевого взаимодействия на `asyncio.open_connection` и бинарной упаковки `struct.pack / unpack`.
* **Обоснование:**
  * Полный контроль над поведением сокета: обработка полуоткрытых соединений, точные таймауты, учет флагов качества данных (`GOOD`/`BAD`).
  * Прозрачность кода для учебных целей и отладки: протокол Modbus TCP тривиален (7 байт MBAP + PDU) и не требует десятков внешних зависимостей.

### 2.3. Хранение данных: SQLite3 в режиме WAL
* **Решение:** Встроенная СУБД SQLite с включенным режимом Write-Ahead Logging (`PRAGMA journal_mode=WAL;`).
* **Обоснование:**
  * Не требует установки и администрирования отдельных СУБД (PostgreSQL, InfluxDB).
  * Режим WAL позволяет одновременно читать данные веб-серверу и асинхронно дописывать телеметрию без взаимных блокировок.

### 2.4. Веб-интерфейс: FastAPI + WebSockets + Vanilla JS
* **Решение:** FastAPI для бэкенда и чистый HTML5/JS для операторского экрана.
* **Обоснование:**
  * FastAPI нативно интегрирован с `asyncio` и ASGI-сервером (`uvicorn`), обеспечивая миллисекундную передачу WebSocket-пакетов.
  * Отсутствие Node.js/Webpack/Vite на фронтенде гарантирует, что проект запустится у любого проверяющего без установки гигабайтов `node_modules`.

## 3. Декларация инструментального контура (7 позиций КТП)

В соответствии с регламентом КТП определены инструменты по всем 7 направлениям инженерного контура и маршрут их подключения в течение семестра:

| № | Позиция КТП | Выбранный инструмент | Назначение в проекте | Текущий статус (КТ-1) | Маршрут подключения в семестре |
|---|---|---|---|---|---|
| **1** | **Подготовка окружения / сборка** | Python `venv`, `Docker` / Compose | Изоляция окружения Python и воспроизводимый запуск мультисервисного контура в контейнере | Реализован `venv` + активационные скрипты | На КТ-2 добавляется `Dockerfile` и `docker-compose.yml` |
| **2** | **Управление зависимостями** | `pip`, `requirements.txt` | Декларация и воспроизводимая установка внешних библиотек | Реализован `requirements.txt` с фиксированными библиотеками | На КТ-2 добавление `pip-tools` для компиляции freeze-хэшей |
| **3** | **Автоматические тесты** | `pytest`, `pytest-asyncio` | Модульное и интеграционное тестирование шины, фильтра и бинарных протоколов | Написаны тесты `test_bus.py`, `test_deadband.py`, `test_modbus.py` | На КТ-2 покрытие асинхронных сбоев сети и транзакций SQLite |
| **4** | **Статический анализ** | `ruff`, `mypy` | Быстрый линтинг, форматирование кода и статическая проверка типов | Выбран `ruff`, запуск локально | На КТ-2 внедрение `mypy` на модели данных, интеграция в pre-commit |
| **5** | **Отладка и диагностика** | `logging`, CLI `--check` | Трассировка событий сети, разбор ошибок сокетов и самодиагностика при старте | Настроен стандартный `logging` (INFO/DEBUG) и режим `--check` | На КТ-2 добавление структурированных JSON-логов для аварий |
| **6** | **Профилирование** | `cProfile`, `tracemalloc`, `py-spy` | Замер накладных расходов памяти шины и CPU-времени при фильтрации 1000+ тегов/сек | Декларирован метод замера через модуль `cProfile` | На КТ-3 проведение эксперимента по замеру производительности фильтра Deadband |
| **7** | **Автоматические проверки в CI** | GitHub Actions | Автоматический запуск тестов и линтера при каждом Push и Pull Request | Создан конфигурационный файл `.github/workflows/ci.yml` | На КТ-2 добавление матрицы версий Python (3.11, 3.12) |

---

## 4. Последствия

* **Положительные:** Минимальный порог входа для нового участника команды, нулевая зависимость от внешней инфраструктуры, предсказуемый запуск за 30 секунд.
* **Отрицательные / Ограничения:** При росте масштаба свыше 500 тегов потребуется вынос архивации в отдельную Time-Series СУБД (будет оформлено как ADR-002 при необходимости).
